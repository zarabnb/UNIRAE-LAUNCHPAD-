# UNIRAE V2.34 — Graduation integrity and admin handoff

## Changes in this source revision

### Liquidity migration integrity
- Validates token0/token1 for both newly created and pre-existing V2 pairs.
- Requires a pair to have zero reserves and zero LP total supply before seeding.
- Handles unsolicited token/Wrapped Native balances on a zero-reserve pair by calling the V2 `skim` function before seeding. Swept assets are returned to the configured LP beneficiary, rather than being left in the coordinator or influencing the launch pool.
- Measures the coordinator's actual LP-token balance before and after the router call and requires the delta to equal the router's reported liquidity.
- Verifies post-migration pair reserves against the actual token and Wrapped Native balances.
- Returns leftover Wrapped Native to the beneficiary, in addition to token and native-asset dust.
- Verifies the exact amount of launch tokens pulled from the curve and resets router approval before granting the one-time allowance.

### Buyback delivery and transfer-tax compatibility
- A real Unirae token applies buy tax when tokens move from an AMM pair. Sending buyback output directly to a non-exempt sink would therefore deliver less than the router's reported output and make the executor's measured-delivery guard revert.
- The canonical `0x...dEaD` sink is now permanently tax-exempt in every newly launched token.
- The buyback executor only accepts that canonical sink and now requires the router's Wrapped Native address to contain code.
- A Foundry regression scenario checks that an AMM-to-sink transfer arrives in full and that the token owner cannot remove the sink exemption.

### Factory coordinator binding
- The factory now checks that a proposed migration coordinator reports the exact curve and token being configured.
- It also requires the coordinator's router and LP locker dependencies to contain code.
- This prevents accidental or mismatched coordinator wiring. It does not prove that the configured router or locker is an official deployment; deployment configuration still requires address verification.

### Administrative ownership and buyback execution
- Factory, fee-vault, launched-token, and equity-registry ownership now use two-step handoffs. A proposed owner must explicitly accept before control changes.
- Fee-vault buyback execution is owner-only. Previously, any caller could choose `minTokensOut`; an attacker could trigger the entire accrued reserve with a deliberately weak minimum. Restricting execution closes that public trigger path. A reviewed multisig should own the vault and choose a meaningful minimum output for each execution.
- Two-step ownership reduces accidental transfers to mistyped or non-responsive addresses.
- This is not a timelock or multisig by itself. Production ownership should be handed to a reviewed multisig/timelock.

## Added Solidity test scenarios

`contract-tests/v1_2/UniraeV2MigrationCoordinator.t.sol` adds mocks and scenarios for:
- Fresh pair creation and LP lock accounting.
- Reusing a pre-created empty pair that contains unsynced donations, sweeping and refunding those donations.
- Rejecting a router that reports more LP tokens than it actually minted.

Factory, fee-vault, token, and equity-registry Foundry tests now also cover two-step ownership acceptance. The fee-vault test asserts that an arbitrary external caller cannot trigger a buyback or choose the slippage floor.

## Verification status

The Python static guard suite and production environment-shape preflight are run for this release. The Solidity test source is added, but it has **not** been compiled or executed in this environment because neither `solc` nor `forge` is installed and package downloads cannot resolve from the runtime. Do not treat these tests as runtime proof until the project is compiled and run with Foundry.

No RPC-backed testnet deployment, live graduation, independent audit, or multisig handoff is claimed by this revision.
