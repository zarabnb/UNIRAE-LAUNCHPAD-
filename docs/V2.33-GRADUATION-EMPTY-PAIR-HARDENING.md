# V2.33 — Graduation empty-pair griefing hardening

## Finding
The migration coordinator previously required the V2 factory to return no pair. On standard V2 DEXes, anyone can create a token/Wrapped Native pair once the token address is public. Creating an empty pair could therefore permanently block graduation without adding liquidity.

## Change
The coordinator now reuses an existing pair only after checking that: its bytecode exists; `token0` and `token1` match the launch token and configured wrapped-native asset; and both reserves are zero. If no pair exists, the coordinator creates it. A pre-seeded pair is still rejected so graduation cannot unknowingly seed a manipulated initial price.

## Remaining risk
A third party can still pre-seed the pair and cause migration to revert. This is a deliberate fail-safe rather than accepting an externally established price. A stronger production design would use a dedicated factory/pool deployment or an audited price/range policy. This change removes the trivial empty-pair griefing vector; it does not eliminate all pair-creation denial-of-service risk.

## Verification
A source-level regression guard checks pair identity and zero reserves. Solidity compilation and Foundry runtime tests remain required before deployment.
