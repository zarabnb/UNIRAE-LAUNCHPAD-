# V2.7 — Chain-bound wallet authentication

## Changes
- Wallet nonce requests now require an explicit positive EVM `chainId`.
- A challenge is issued only for a chain that has an RPC configured in the backend chain registry.
- The signed login message includes that chain ID and an allowlisted origin URI.
- The nonce row persists the chain ID; successful verification carries it into the HMAC session.
- `/v1/auth/me` reports the authenticated chain binding.
- Session validation rejects missing, non-integer, or non-positive chain IDs.
- Migration `0003_wallet_nonce_chain_id` invalidates outstanding pre-upgrade nonces before adding the required chain ID column. This intentionally forces users to request a fresh challenge after migration.

## Client API change
`POST /v1/auth/nonce` body:

```json
{"address":"0x...","domain":"app.example","chainId":97}
```

Clients must switch to the intended EVM chain before requesting a challenge. The server signs the declared chain into the challenge and returns the same chain ID in the session. The client should compare the session chain ID with the wallet's active chain before chain-specific writes.

## Security notes
- This is EIP-191 personal-message authentication with a SIWE-shaped message, not a full implementation of the EIP-4361 parser/validator.
- Chain binding prevents a session from being silently reused as if it were issued for another chain, but the backend must still authorize each write against its own allowed-chain policy.
- The existing process-local rate limiter is not a distributed rate limiter. Production requires a shared gateway/Redis limiter, TLS, secret rotation, session revocation, monitoring and abuse controls.
- The `WalletNonce` migration deletes all outstanding nonce rows to avoid accepting legacy chain-unbound challenges.
