# V2.20 — LP locker hardening

## Changes
- `lock` and `withdraw` now share a reentrancy guard around external LP-token calls.
- LP token addresses must contain contract code.
- Deposits must increase the locker balance by exactly the requested LP amount; fee-on-transfer and otherwise inexact LP tokens are rejected.
- Withdrawals verify both the locker debit and beneficiary credit equal the recorded amount.
- The lock record is marked withdrawn before the external token transfer; any failure reverts the state change atomically.

## Rationale
The locker is a custody boundary for graduation LP tokens. Non-standard token transfer behavior can otherwise create undercollateralized lock records or cause beneficiaries to receive less LP than the recorded lock amount. The reentrancy guard prevents callbacks from entering another lock/withdraw operation while a token call is in progress.

## Verification status
Static source checks and regression-test presence checks are included in `tests/v2.20-static-check.py`. Foundry runtime execution is still required; this environment does not include Foundry/solc. Only reviewed standard AMM LP tokens should be accepted in production.
